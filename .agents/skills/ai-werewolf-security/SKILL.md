# AI 狼人杀项目安全开发 Skill

本 Skill 适用于本仓库的安全审查和安全敏感改造。它迁移的是 Popia Skill 中的开发纪律，不迁移 Popia 的项目名、端口、框架、数据库、命令或部署环境。

## 一、开始前先确认项目事实

在仓库根目录：

- 阅读适用的 `AGENTS.md`、`README.md`、`TECHNICAL_DOCUMENT.md` 及对应模块说明。
- 检查 `git status --short --branch`、当前分支、最近提交和目标文件差异；保留用户已有修改，不执行 reset、clean，不覆盖本地配置，不混入无关改动。
- 重新核实目录、模块、依赖和测试命令。当前仓库快照中后端在 `backend/`，前端在 `frontend/`，提示词在 `templates/`；不能假定这些信息以后不变。
- 从脚本、Maven 配置、CI 和项目文档确认测试、构建、迁移及部署命令；不要猜命令，也不要用破坏性操作探测环境。
- 在审查和计划中区分：**仓库已验证事实、推断、未知事项、需要项目负责人的决定**。

以下只是已检查快照中的线索，使用时必须复查：项目采用 Java 8 / Spring Boot 2.5.14 与 Vue 3；`frontend/src/utils/apiKeys.js` 曾把模型 Key 存在浏览器 `localStorage`，多个前端页面存在直接请求模型 Provider 的逻辑；`AiPlayer` 实体含有服务端 API Key 字段；后端已有 `GameStateProjection` 和相关测试；`application.yml` 曾含数据库与 JWT 默认配置。不要在 Skill、报告、测试数据或聊天中抄录任何密钥值；不能仅凭默认值断言它是真实生产凭证。

## 二、高风险计划与授权门禁

涉及密钥、认证/授权、隐藏游戏状态、模型 Provider 路由、用户可配置的 Provider URL、数据库结构、生产配置、外部服务或跨层安全边界时：

1. 先梳理数据流、信任边界、影响模块、兼容与回滚路径。
2. 先给出影响面计划，至少包含威胁、拟采取的控制、测试和需要负责人决定的事项。
3. 用户要求先审查/规划或尚未授权高风险实施时，先停在计划阶段等待确认。用户确认已同意的计划并要求实施后，直接开始，不重复泛泛确认。
4. 数据库迁移、生产环境操作、凭证轮换、使用真实 Key 的外部模型测试和部署均需分别获得针对该环境/操作的授权；一般的代码修复请求不包含这些授权。
5. 若无法安全验证已授权改动，先不执行风险操作，说明阻塞点和下一步安全做法。

不得无证据断言漏洞已被利用或配置值是真实密钥。对疑似泄露凭证不打印内容；在授权范围内提出撤销/轮换建议。

## 三、密钥与配置保护

- 把模型 Key、数据库口令、JWT 签名密钥、Cookie、令牌及语音 Provider 凭证都按秘密信息处理。
- Provider Key 不得放在 Vue 代码、浏览器存储、URL、查询参数、前端构建变量、Source Map、Prompt、分析事件或日志中；前端密码框和掩码不是安全边界。
- 模型调用应经由经过认证的后端网关。密钥来自部署密钥服务或未提交的本地环境配置，遵循最小权限、环境隔离和轮换。若产品必须允许用户自带 Key，先明确归属、静态加密/密钥管理、访问控制、删除及禁止明文回读的契约。
- 缺少必需密钥时应安全失败；不得静默回退到仓库内默认秘密。配置样例只放占位符，和生产配置分离。
- 日志和异常中脱敏 Authorization Header、含密请求体及 Provider 原始错误；检查成功和失败路径。
- 若 Provider URL 可由用户配置，校验协议和域名白名单，并按部署环境阻止访问 loopback、私网、链路本地等目标及不安全重定向，避免后端成为 SSRF 代理。

## 四、游戏状态和动作必须由服务端把关

- 身份、阶段、角色权限、生死状态、合法目标、技能次数、投票与胜负规则应由服务端游戏/规则服务裁定；前端隐藏控件或 Prompt 声明不能替代授权。
- 每个 AI 角色只接收后端生成的字段白名单投影。默认拒绝；分别测试公开信息、自身私有信息、队友可见信息和角色专属信息。复用或扩展 `GameStateProjection` 前，先检查实际调用路径和语义。
- 玩家发言、对局历史、检索文档和模型先前输出均为不可信数据；它们不能覆盖系统/规则指令、扩大工具权限或取得隐藏状态。
- 发言和动作使用不同的数据契约。动作按版本化 Schema 解析后，服务端还要验证操作者、阶段、角色、目标、技能资源、当前状态版本和幂等键，再允许状态变更。
- 非法、越权、过期或不可能的动作不得改变状态；仅在有界重试后执行明确的角色/规则兜底（如跳过/弃权），不得从自由文本猜动作。
- 胜负判定、夜间结算、投票计数和技能消耗由确定性规则逻辑负责；模型推理或理由摘要不作为裁决依据。

## 五、模型调用的可靠性与隔离

对每条模型调用链（游戏、API 测试、对话测试、裁判/分析和相关语音）确认：

- 调用者身份、用户/房间归属、模型选择和凭证来源。
- 请求大小与上下文限制、连接/读取超时、有限重试、用户/房间/Provider 限速与并发、Token/费用预算。避免重试风暴及动作重复执行。
- 返回统一且安全的错误；不向客户端泄露密钥、内部堆栈、隐藏状态或未脱敏 Provider 原始响应。
- Provider 专属认证头和响应格式限制在适配层；测试使用 Stub/Fake，不依赖 CI 真实密钥或产生费用。使用真实 Provider 前需单独确认数据出境范围及成本授权。
- 设计故障兜底以保障对局可继续，但不得悄悄伪造拥有更高权限的决策；记录排查所需的模型/Provider/结果元数据，同时避免保存密钥和不必要的隐藏内容。

## 六、分层改动与数据库迁移

按仓库真实结构做最小且完整的安全改动。跨层任务应写明前端、Controller/API、游戏服务/规则、持久层、模型网关及可选异步/语音模块的职责和接口；项目没有的 Domain、Repository 或 Worker 层不要强行虚构。

数据库变更需：

- 审查具体迁移及前后兼容、数据规模、锁表/默认值/索引、发布顺序和回滚/恢复方案。
- 需要时将迁移与应用发布分开；未得到对目标数据库/环境的明确授权，不执行迁移。
- 不推断本地或测试命令指向测试库；验证连接目标时不得打印凭证。
- 尽可能在获准的临时/测试数据库验证；如果未验证，明确报告。

## 七、验证清单

先查明并运行仓库已有的相关测试命令，再按风险补足。适用时覆盖：

- 密钥缺失、掩码、更新/删除后不回显；源码、构建产物、API 响应和日志中无密钥。
- 按用户/角色区分公开和私有状态投影；角色切换、队友信息、死亡、阶段变更及越权读取。
- Schema 错误、角色/阶段/目标非法、技能耗尽、状态过期、重复请求和并发写入时，断言状态没有被错误修改。
- 玩家发言/历史/检索内容中的 Prompt 注入不会取得额外状态或工具权限。
- Provider 超时、限流、5xx、空/畸形响应、重试上限、预算耗尽和兜底路径。
- 游戏房间、AI 玩家、密钥/配置接口的身份认证与资源归属；未授权请求必须失败关闭。
- 若 Provider URL 可配置，覆盖 SSRF 与重定向策略。

按风险运行针对性单测/集成测试及必要的前后端构建或静态检查。只有实际执行过才报告通过；代码测试不能冒充真实 Provider、部署或生产验证。不得为了测试而擅用真实密钥。

## 八、交付说明

结束前检查 `git diff --check`、`git status --short` 和完整目标差异，排除意外配置、密钥、生成物或无关修改。除非用户明确授权，不提交、不推送、不建 MR、不部署、不轮换密钥、不运行迁移。

总结：改了哪些文件及改善的安全边界；实际运行了哪些测试及结果；仍存在的风险、未知或未验证行为；需要单独授权的迁移/轮换/部署；是否保留了原有未提交工作。

## 九、本项目常见误区（每次重新核实）

- API 响应有脱敏 Key，不代表浏览器不会直连 Provider；要检查浏览器网络请求和存储。
- `GameStateProjection` 有单测，不代表所有模型调用都使用正确投影；必须追踪调用方和状态组装链。
- Redis 可用不等于任务持久化、幂等或限流正确；需验证具体实现。
- 本地/测试配置和构建通过不代表生产密钥、数据库目标、CORS 或网络可达性正确。
- 升级依赖不是修复信任边界的替代品；提出框架升级前先评估 Java/Spring 兼容和迁移影响。
